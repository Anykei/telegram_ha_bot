## Дополнительные исправления после повторного ревью

изменений отдельная схема не требуется; условия и результаты перечислены ниже.

| Проблема | Исправление | Регрессионная проверка |
|---|---|---|
| Событие продлевает запись между проверкой срока и переводом в `ready`, но продолжение теряется | `mark_ready_if_due` завершает только активную запись с истёкшим актуальным сроком; при продлении worker продолжает цикл. Создание/продление и завершение сериализованы через `BEGIN IMMEDIATE`; срок cooldown фиксируется в той же транзакции и читается из БД при новом событии | Событие до завершения сохраняет текущую запись; после завершения создаёт новую при истёкшем cooldown. Одновременное событие и завершение проверены на файловой SQLite в WAL. Сохранены ручная остановка, pre-roll metadata, терминальные статусы и cooldown |
| Разрешённое отдельно устройство недоступно через меню закрытой для пользователя комнаты | Список комнат и callback используют общую проверку навигации `can_open_room`: комната доступна при наличии разрешённого активного устройства. Камеры и соседние устройства остаются закрыты; обычный пользователь и root сохраняют доступ |

Пока pre-roll ещё формируется после истечения срока, worker повторно проверяет
сессию каждые 100 мс. Новое продление возобновляет запись, не дожидаясь завершения

прикрепление видео по-прежнему нужно проверить на RTSP-стенде.

Добавлено пять тестов на схеме из реальных миграций. Рабочая БД, HA и Telegram
при этих проверках не использовались; дополнительных миграций не требуется.

## FIX-03: контракт и фактическая совместимость

Реализация находится в `src/ha/intent_recognition.rs` и `src/core/readonly.rs`.
Зависимость передаётся в обработчик как `ReadonlyHa`; объект создаётся в маршруте
readonly без добавления обязательных полей в AppConfig или options.json.
Чтение состояний использует GET `/api/states/{entity_id}`; температура климатических
устройств при необходимости получает единицу через GET `/api/config`.
WSS поддерживается через native-tls.

| Intent | Локальная операция |
|---|---|
| HassGetState без state | Состояния и единицы измерения |
| HassGetState со state | Сравнение свежих состояний; количество, список, «есть ли», «все ли» |
| HassGetState с разрешённым attribute | Чтение одного из явно перечисленных скалярных атрибутов |
| HassClimateGetTemperature | current_temperature для climate или состояние температурного sensor |
| HassGetWeather | Текущее состояние погоды и температура |

Для вопроса о погоде без слотов HA debug не формирует targets. Добавлено чтение
только ID weather-сущностей через **фиксированный** шаблон `/api/template`, после
которого выполняются обычные проверки ACL до чтения состояний. В шаблон не
подставляются пользовательский текст или слоты. Несопоставленная с БД сущность
доступна только root согласно прежней политике root.

Сводка отвечает сразу на количество/список/any/all: диагностический ответ не
содержит ключ шаблона ответа обычного Conversation. Неизвестные состояния не
подменяются нулём, `нет` или `выключено`. Очень длинные списки сокращаются по
целым строкам, счётчики рассчитываются по полному разрешённому набору.

Проверенная установленная версия — **HA 2026.6.4**. Её
[HTTP/WebSocket-контракт](https://github.com/home-assistant/core/blob/2026.6.4/homeassistant/components/conversation/http.py)
и [реализация распознавания](https://github.com/home-assistant/core/blob/2026.6.4/homeassistant/components/conversation/default_agent.py)
проверены перед запросами. Использовались только диагностическое распознавание,
GET и фиксированный шаблон чтения списка ID погоды. Conversation process,
сервисы и исполнение intent не вызывались.

| Проверочные вопросы | Результат на настроенном HA 2026.6.4 |
|---|---|
| «какая температура» / “what is the temperature” | Без уточнения датчика не распознаны; успешные именные вопросы с комнатой приведены ниже |
| «сколько ламп включено» / “how many lights are on” | HassGetState, domain/state, 0 targets |
| «какие окна открыты» / “which windows are open” | HassGetState, domain/device_class/state, 0 targets |
| «все лампы выключены» / “are all lights off” | HassGetState, domain/state, 0 targets |
| «какая погода» / “what is the weather” | HassGetWeather без слотов/targets; фиксированный каталог вернул одну weather-сущность, GET состояния успешен |
| Вопросы о состоянии трёх имеющихся температурных датчиков по их HA-именам, ru/en | 6 запросов, совпадающая цель не найдена; сквозной ответ не подтверждён |
| Вопросы по трём доступным Assist температурным датчикам с именем **и комнатой**, ru/en | **6 из 6**: распознавание, разрешение целей, чтение и формирование ответа успешны |

Для проверенных температурных датчиков установлены повторяющиеся имена:
по два датчика с одним именем. Добавление комнаты устранило неоднозначность.
Список exposure прочитан диагностически: Assist доступны 41 сущность, включая
10 температурных датчиков. Настройки exposure не менялись. Причина отсутствия
целей для общих вопросов о свете/окнах не установлена. Эти ответы не доказывают
ни наличие устройств нужных доменов, ни корректность настройки их распознавания.
Состояния и имена реальных сущностей в отчёт и вывод теста не включались.
Для проверки именных вопросов получены только ID/имена температурных датчиков
через фиксированный шаблон чтения метаданных; произвольный пользовательский текст
в шаблон не подставлялся. Имена и комнаты использовались только для диагностического
распознавания и чтения. Для первого запуска при повторяющихся именах указывайте
комнату либо назначьте уникальные имена/alias в HA.

В HA 2026.6.4 `_get_debug_targets` не применяет слот floor. Поэтому вопросы
со floor отклоняются, чтобы не отвечать по всем этажам. Поддержка floor разрешена
для ветки 2026.9.x, проверенной по исходникам; остальные версии требуют проверки
этого контракта. Обычные запросы без floor используют проверку схемы ответа.

Нераспознанные фразы, sentence triggers, неизвестные intent и несовместимые
ответы дают отказ без перехода в full. Распознавание использует каталог HA;
изоляцию результатов по Telegram ACL обеспечивает бот. Произвольные custom
intent и дополнительные пути обычного Assist не объявляются поддержанными.
