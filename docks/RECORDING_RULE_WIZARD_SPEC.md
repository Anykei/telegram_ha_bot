# Спека: мастер создания правил записи камер

## Цель

Упростить создание правил записи камер в Telegram-боте, чтобы обычный
пользователь не набирал вручную хрупкие строки вида:

```text
entity_id;operator;from_state;to_state;value
```

Существующий текстовый формат остается как расширенный режим. Новый основной
путь - мастер с кнопками, где пользователь собирает правило из понятных частей:

- выбрать источник события, который запускает проверку правила;
- выбрать одно или несколько условий;
- выбрать логику условий: `all` или `any`;
- настроить длительность записи и срок хранения;
- создать готовое правило без ручного ввода строк.

Мастер должен поддерживать не только двери/окна, но и более общий сценарий:
`binary_sensor`, `sensor` и `number`. Например: писать с камеры, когда
температура изменилась и стала выше 28 градусов, или когда дверь открылась и
включена охрана.

## Не Цель

- Не переписывать движок правил.
- Не удалять текущий текстовый ввод.
- Не делать редактор произвольных выражений или скриптов.
- Не менять формат текущего текстового расширенного ввода без отдельной
  миграции.
- Не создавать автоматизации в Home Assistant. Правила остаются внутри бота.

## Текущее Состояние

Правила уже хранятся в таблицах:

- `camera_recording_rules`
- `camera_recording_rule_conditions`
- `camera_recording_rule_groups`
- `camera_recording_rule_group_items`

Matcher уже умеет:

- `changed_to`
- `changed_from_to`
- `is`
- `is_not`
- `contains`
- `above`
- `below`
- логику `any` и `all`

То есть ядро достаточно мощное. Основная проблема - UX создания правил.

## Вход В Мастер И Целевая Модель

Добавить мастер в экран:

```text
Админка -> Камеры -> Комната -> Правила записи
```

На экране правил заменить одну кнопку добавления на две:

```text
➕ Мастер
⌨️ Расширенно
```

`Расширенно` открывает существующий текстовый ввод.

`Мастер` запускает пошаговый сценарий.

Целевая модель мастера:

```text
source -> condition -> + condition -> + condition -> create
```

Где `source` - сущность, событие которой будит правило, а `condition` -
проверка состояния источника или другой сущности на момент события.

## Пользовательский Сценарий

### 1. Выбор Камеры

Если в комнате нет активных камер:

```text
В этой комнате нет активных камер.

[➕ Добавить камеру]
[Назад]
```

Если в комнате одна активная камера, мастер выбирает ее автоматически.

Если камер несколько:

```text
Выберите камеру

[USB камера]
[Камера вход]
[Назад]
```

### 2. Выбор Источника События

Показать сущности из всех комнат, которые могут запустить правило. Список нужно
разбить по комнатам: текущая комната камеры идет первой, остальные комнаты ниже
по имени. Это позволяет собрать правило вида "камера в прихожей пишет, если
сработал датчик из другой комнаты".

Пример:

```text
Прихожая
[Замок Дверь · zamok_contact]

Кухня
[Температура кухня · kitchen_temperature · sensor]
```

Приоритет кандидатов:

1. `binary_sensor` с `device_class`:
   - `door`
   - `window`
   - `opening`
   - `garage_door`
   - `motion`
   - `occupancy`
   - `presence`
2. `sensor` и `number`; числовые и известные numeric `device_class` показывать
   выше остальных:
   - `temperature`
   - `humidity`
   - `illuminance`
   - `power`
   - `energy`
   - `battery`
   - `voltage`
   - `current`
   - `pressure`
   - прочие numeric sensors
3. `switch`
4. `light`
5. прочие `sensor`
6. прочие `binary_sensor`

Подпись кнопки:

```text
<имя устройства> · <короткий entity_id> · <тип>
```

Пример:

```text
[Замок Дверь · zamok_contact]
[Температура кухня · kitchen_temperature · sensor]
```

Если подходящих сущностей нет:

```text
В доступных комнатах не найдено подходящих источников для правила.

[⌨️ Расширенный ввод]
[Назад]
```

### 3. Выбор События Источника

Набор кнопок зависит от типа сущности.

Для двери/окна:

```text
Когда записывать?

[Открытие и закрытие]
[Только открытие]
[Только закрытие]
[Любое изменение]
[Расширенно]
```

Для движения/присутствия:

```text
Когда записывать?

[Движение появилось]
[Движение пропало]
[Оба события]
[Любое изменение]
[Расширенно]
```

Для `switch`/`light`:

```text
Когда записывать?

[Включение]
[Выключение]
[Включение и выключение]
[Любое изменение]
[Расширенно]
```

Для числового `sensor`/`number`:

```text
Когда запускать проверку?

[Любое изменение]
[Стало выше значения]
[Стало ниже значения]
[Расширенно]
```

В будущей версии после миграции matcher можно добавить отдельные события:

```text
[Пересекло вверх]
[Пересекло вниз]
```

Разница:

- `Стало выше значения` означает: пришло событие по источнику, новое или текущее
  значение выше порога.
- `Пересекло вверх` означает: предыдущее значение было ниже или равно порогу, а
  новое стало выше. Это требует нового оператора в matcher.

Рекомендованные значения по умолчанию:

- дверь/окно: открытие и закрытие;
- движение/присутствие: движение появилось;
- switch/light: включение и выключение;
- sensor/number: любое изменение, затем условие по порогу.

### 4. Условия

После выбора источника мастер показывает список условий правила.

Первое условие создается из выбранного источника. Пользователь может добавить
дополнительные условия:

```text
Условия правила

1. Температура кухня изменилась
2. Температура кухня выше 28

Логика: все условия

[➕ Добавить условие]
[Логика: все/любое]
[Далее]
[Расширенно]
```

Поток добавления условия:

```text
Выберите сущность, список разбит по комнатам
-> выберите оператор
-> введите значение, если нужно
-> сохранить условие
```

Поддерживаемые операторы без миграции БД:

- `is`: состояние равно значению;
- `is_not`: состояние не равно значению;
- `contains`: состояние содержит текст;
- `above`: числовое состояние выше значения;
- `below`: числовое состояние ниже значения;
- `changed_to`: новое состояние равно значению, либо любое новое состояние, если
  значение не задано;
- `changed_from_to`: переход из одного состояния в другое.

Для обычного пользователя названия должны быть человекочитаемыми:

- `равно`;
- `не равно`;
- `содержит`;
- `выше`;
- `ниже`;
- `изменилось на`;
- `изменилось с ... на ...`.

Логика условий:

- `all`: писать, только если все условия истинны;
- `any`: писать, если истинно любое условие.

По умолчанию:

- один источник без дополнительных условий: `any`;
- источник плюс дополнительные условия: `all`.

### 5. Длительность Записи После События

Показать пресеты:

```text
Сколько писать после события?

[30с] [60с]
[120с] [300с]
```

Ограничения:

- минимум: 5 секунд;
- максимум: `camera_recording_max_tail_seconds`.

Дефолт:

- 60 секунд для двери/окна/switch/light;
- 120 секунд для движения.

### 6. Срок Хранения

Показать пресеты:

```text
Сколько хранить записи?

[7д] [15д]
[30д] [90д]
```

Дефолт:

- настройка `CAMERA_RECORDING_DEFAULT_RETENTION_DAYS`;
- если настройки нет, 30 дней.

### 7. Время Активности

Полная модель времени активности описана в
`docks/recording-rule-groups/SPEC.md`.

Шаг показывается после срока хранения и перед выбором групп.

```text
Когда правило активно?

[Всегда]
[Ночь 22:00-07:00]
[День 08:00-20:00]
[Свое время]
```

Дефолт: `Всегда`.

`Свое время` открывает ручной ввод:

```text
Введите время в формате HH:MM-HH:MM.
Например: 22:00-07:00
```

Окно может пересекать полночь. Время считается в локальной таймзоне бота.

В MVP можно реализовать этот шаг после основной версии мастера. До реализации
поля времени правило создается как `Активно: всегда`.

### 8. Группы Правил

Полная модель управления группами описана отдельно:
`docks/recording-rule-groups/SPEC.md`.

Шаг выбора групп показывается в конце, после сборки источника, условий, tail,
retention и времени активности, но перед финальным подтверждением.

Группы выбираются на одной странице как multi-select. При нажатии на группу она
отмечается или снимается. Кнопка `Далее` доступна всегда: если пользователь не
выбрал ни одной группы, правило создается без групп.

MVP-семантика: правило работает только когда включены все выбранные группы и
текущее время попадает в окно активности. Выключенная группа ставит связанные
правила на паузу.

```text
Группы правила

[ ] Двери
[✓] Охрана
[ ] Ночь

[Далее]
[Назад]
```

Если групп нет, шаг можно показать пустым экраном с одной кнопкой `Далее`, либо
пропустить автоматически.

Автоматически создавать группы нельзя. Мастер показывает только уже существующие
группы. Группы можно добавить позже из детального экрана правила.

### 9. Подтверждение

Финальный экран:

```text
Создать правило записи?

Камера: USB камера
Датчик: Замок Дверь
Событие: открытие и закрытие
Писать после события: 60с
Max segment: 300с
Cooldown: 0с
Хранить: 30д
Активно: всегда
Группы: Двери

Будут созданы условия:
off -> on
on -> off

[✅ Создать]
[✏️ Расширенно]
[Отмена]
```

Пример для температуры:

```text
Создать правило записи?

Камера: USB камера
Источник: Температура кухня
Событие: любое изменение
Логика: все условия
Условия:
1. Температура кухня изменилась
2. Температура кухня выше 28
Писать после события: 60с
Max segment: 300с
Cooldown: 30с
Хранить: 30д
Активно: 22:00-07:00
Группы: нет

[✅ Создать]
[➕ Добавить условие]
[✏️ Расширенно]
[Отмена]
```

`Создать` пишет правило в БД.

`Расширенно` показывает сгенерированный текстовый блок для копирования/правки и
переводит диалог в существующий режим текстового ввода. Буквально
предзаполнить поле ввода Telegram нельзя.

## Генерация Правил

В текущей БД нет отдельного поля `source`. Источник события и дополнительные
условия сохраняются как строки `camera_recording_rule_conditions`.

Правило работает так:

- если событие пришло по entity из условия, matcher проверяет новое/старое
  состояние события;
- если условие относится к другой entity, matcher проверяет ее текущее состояние;
- `condition_logic = all` позволяет собрать сценарий "источник изменился и все
  условия сейчас истинны";
- `condition_logic = any` позволяет собрать сценарий "любое из условий может
  запустить запись".

### Дверь/Окно: Открытие И Закрытие

```text
<Название датчика>: открытие или закрытие
<camera_id>
any
<entity_id>;changed_from_to;off;on;
<entity_id>;changed_from_to;on;off;
<tail_seconds>
<max_segment_seconds>
0
<retention_days>
```

Пример для текущей двери:

```text
Замок Дверь: открытие или закрытие
3
any
binary_sensor.zamok_contact;changed_from_to;off;on;
binary_sensor.zamok_contact;changed_from_to;on;off;
60
300
0
30
```

### Только Открытие

```text
<entity_id>;changed_from_to;off;on;
```

### Только Закрытие

```text
<entity_id>;changed_from_to;on;off;
```

### Движение Появилось

```text
<entity_id>;changed_from_to;off;on;
```

Для motion/presence правил дефолтный `cooldown_s` должен быть 30 секунд, чтобы
частые события движения не создавали слишком шумный поток записей.

### Движение Пропало

```text
<entity_id>;changed_from_to;on;off;
```

### Любое Изменение

Для бинарных сущностей можно использовать два явных перехода:

```text
<entity_id>;changed_from_to;off;on;
<entity_id>;changed_from_to;on;off;
```

Для любых сущностей можно использовать `changed_to` без целевого значения:

```text
<entity_id>;changed_to;;;
```

Это означает "любое новое состояние". Для `unknown`/`unavailable` matcher должен
вести себя так же, как сейчас ведет себя существующий оператор.

### Температура Стала Выше Порога

Сценарий пользователя:

```text
Когда температура кухни изменилась и стала выше 28, писать 60 секунд.
```

Генерируемое правило без новой миграции:

```text
Температура кухня: выше 28
3
all
sensor.kitchen_temperature;changed_to;;;
sensor.kitchen_temperature;above;;;28
60
300
30
30
```

Здесь первое условие будит правило на любое изменение температуры, второе
проверяет, что новое или текущее значение выше `28`.

Это не то же самое, что "пересекло 28 снизу вверх". Если температура уже была
`29` и изменилась на `30`, правило тоже подойдет. Для подавления повторов нужен
`cooldown_s`.

### Температура Пересекла Порог

Для точного сценария "было ниже или равно 28, стало выше 28" нужен новый оператор
matcher, например:

```text
sensor.kitchen_temperature;crossed_above;;;28
sensor.kitchen_temperature;crossed_below;;;18
```

Это отдельная фаза, потому что потребуется:

- добавить операторы в enum/валидацию;
- обновить `CHECK` constraint или миграцию таблицы условий, если он есть;
- сравнивать старое и новое значения события как числа;
- определить поведение для `unknown`, `unavailable`, пустых и нечисловых
  значений.

До этой фазы мастер показывает "стало выше/ниже", а не "пересекло".

### Источник Плюс Контекстное Условие

Сценарий:

```text
Писать, когда дверь открылась и охрана включена.
```

Генерация:

```text
Дверь: открытие при включенной охране
3
all
binary_sensor.zamok_contact;changed_from_to;off;on;
binary_sensor.security_armed;is;;;on
60
300
0
30
```

Событие приходит от двери, а состояние `binary_sensor.security_armed` берется как
текущее состояние на момент события.

## Защита От Дублей

Перед созданием правила проверить, есть ли активное неудаленное правило с:

- тем же `camera_id`;
- тем же `condition_logic`;
- тем же нормализованным набором условий.

Для сравнения условий порядок не должен иметь значения, кроме случаев, где позже
появятся операторы с явной последовательностью. В текущей модели порядок условий
не влияет на matcher.

Если найдено похожее правило:

```text
Похожее правило уже есть:
<название правила>

[Открыть существующее]
[Создать все равно]
[Отмена]
```

Рекомендуемое действие - открыть существующее.

## Модель Данных

Миграция БД для generic-мастера без `crossed_above/crossed_below` не нужна.
Операторы `is`, `is_not`, `contains`, `above`, `below`, `changed_to` и
`changed_from_to` уже существуют.

Состояние мастера хранится в session/dialogue. Callback payload должен быть
коротким и не должен содержать весь контекст мастера.

Предлагаемое состояние:

```rust
RecordingRuleWizard {
    room_id: i64,
    camera_id: Option<i64>,
    source: Option<WizardSourceDraft>,
    conditions: Vec<WizardConditionDraft>,
    condition_logic: WizardConditionLogic,
    tail_seconds: Option<u32>,
    retention_days: Option<u32>,
    group_ids: Vec<i64>,
}
```

Источник события:

```rust
struct WizardSourceDraft {
    device_id: i64,
    entity_id: String,
    display_name: String,
    domain: String,
    device_class: Option<String>,
    mode: WizardSourceMode,
}

enum WizardSourceMode {
    OpenAndClose,
    OpenOnly,
    CloseOnly,
    Detected,
    Cleared,
    DetectedAndCleared,
    TurnedOn,
    TurnedOff,
    TurnedOnAndOff,
    AnyChange,
    NumericAbove { value: String },
    NumericBelow { value: String },
    // Future phase:
    CrossedAbove { value: String },
    CrossedBelow { value: String },
}
```

Условия:

```rust
struct WizardConditionDraft {
    device_id: i64,
    entity_id: String,
    display_name: String,
    operator: WizardConditionOperator,
    from_state: Option<String>,
    to_state: Option<String>,
    value: Option<String>,
}

enum WizardConditionOperator {
    Is,
    IsNot,
    Contains,
    Above,
    Below,
    ChangedTo,
    ChangedFromTo,
    // Future phase:
    CrossedAbove,
    CrossedBelow,
}

enum WizardConditionLogic {
    All,
    Any,
}
```

При сохранении `WizardSourceDraft` превращается в одно или несколько
`WizardConditionDraft`. Например `OpenAndClose` дает два условия
`changed_from_to`, а `NumericAbove` дает `changed_to` плюс `above`.

## Изменения В Коде

Вероятные файлы:

- `src/bot/router.rs`
- `src/bot/handlers.rs`
- `src/bot/screens/admin/list_actions.rs`
- `src/db/devices.rs`
- `src/db/camera_recording_rules.rs`

Callback payload должен быть компактным. Не передавать `entity_id` и весь
контекст мастера в каждом callback: Telegram callback data имеет маленький лимит,
а `entity_id` легко его съест.

Предпочтительный подход:

- хранить состояние мастера в session/dialogue по `user_id`;
- в callback передавать только короткое действие и небольшой ID/код;
- для выбора entity использовать короткий индекс из списка кандидатов текущего
  шага или ID устройства из таблицы `devices`.

## DB Helper Для Датчиков

Нужны helper для первого cut и generic-мастера:

```rust
list_room_recording_trigger_candidates(room_id, pool)
list_recording_wizard_candidates(current_room_id, pool)
```

Кандидат должен содержать:

- `device_id`;
- `entity_id`;
- отображаемое имя;
- domain;
- `device_class`;
- `room_id`;
- название комнаты;
- текущее состояние, если оно уже есть локально.

Domain брать из `devices.device_domain`, а если поле пустое - из префикса
`entity_id` до точки. `device_class` уже синхронизируется в `devices.device_class`
из Home Assistant.

Фильтр generic-мастера:

- `archived = 0`;
- `entity_id IS NOT NULL`;
- domain в списке:
  - `binary_sensor`;
  - `sensor`;
  - `number`;
  - `switch`;
  - `light`.

Сортировка generic-мастера:

- текущая комната камеры первой;
- далее комнаты по имени;
- внутри комнаты сначала типовые `binary_sensor`, затем numeric
  `sensor`/`number`, затем `switch`/`light`, затем прочие сущности;
- внутри группы сортировать по отображаемому имени и `entity_id`.

Для `sensor` и `number` показывать все поддерживаемые сущности. Известные numeric
`device_class` нужно поднимать выше в списке, но прочие сенсоры тоже остаются
доступны. Ограничения накладываются на этапе выбора оператора и сохранения
условия:

- `above`/`below` доступны только для числовых сценариев или проходят числовую
  валидацию введенного значения;
- текстовые сенсоры могут использовать `is`, `is_not`, `contains`,
  `changed_to`;
- если сочетание entity/operator явно невозможно, мастер показывает понятную
  ошибку и предлагает другой оператор или `Расширенно`.

## Валидация

При создании правила:

- пользователь должен быть `root_user`;
- камера должна принадлежать выбранной комнате и быть включенной;
- источник и все entity из условий должны существовать, быть не archived и иметь
  комнату; комната может отличаться от комнаты камеры;
- `tail_seconds` должен укладываться в лимит конфига;
- `max_segment_seconds` брать из `camera_recording_max_segment_seconds`;
- `retention_days` брать из выбранного значения или дефолта;
- `cooldown_s` по умолчанию:
  - 0 секунд для двери/окна/switch/light;
  - 30 секунд для motion/presence и numeric threshold rules;
- не создавать правило без условий;
- для `above`/`below` значение должно быть числом;
- для `changed_from_to` нужны оба значения;
- для `is`, `is_not`, `contains`, `changed_to` значение может быть текстом;
- не создавать неподдерживаемые сценарии через мастер;
- future-операторы `crossed_*` не показывать в UI до готовности миграции и
  matcher.

## Уведомления

Вопрос про уведомления относится к `notify_enabled` у правила, то есть к
уведомлениям о готовой записи после события, а не к отдельному Telegram-сообщению
админу в момент создания правила.

Решение:

- при создании правила через мастер `notify_enabled` включен по умолчанию;
- отдельное сообщение админу "правило создано" не отправлять, достаточно notice
  на текущем экране;
- переключатель уведомлений остается в детальном экране правила.

## Тесты

Unit tests:

- `OpenAndClose` генерирует два условия: `off -> on`, `on -> off`;
- `OpenOnly` генерирует одно условие: `off -> on`;
- `Detected` для motion генерирует `off -> on`;
- `AnyChange` для `sensor` генерирует `changed_to` без `to_state`;
- numeric `above` генерирует `changed_to` плюс `above` и `condition_logic = all`;
- дополнительное условие на другой entity сохраняется как context condition;
- duplicate detection находит совпадение по camera/logic/conditions;
- сгенерированный advanced text парсится существующим
  `parse_recording_rule_input`;
- callback payload не превышает лимит Telegram.

Manual acceptance:

1. Открыть комнату с одной камерой и одним дверным датчиком.
2. Нажать `Мастер`.
3. Выбрать или подтвердить камеру.
4. Выбрать датчик двери.
5. Выбрать `Открытие и закрытие`.
6. Выбрать `60с`.
7. Выбрать `30д`.
8. Нажать `Создать`.
9. Открыть деталь правила и увидеть два условия.
10. Открыть/закрыть дверь в HA и проверить старт/продление записи.

Manual acceptance для numeric-сценария:

1. Открыть комнату с камерой и `sensor` температуры.
2. Нажать `Мастер`.
3. Выбрать камеру.
4. Выбрать температуру как источник.
5. Выбрать `Стало выше значения`.
6. Ввести `28`.
7. Проверить экран условий: `температура изменилась` и `температура выше 28`.
8. Выбрать `60с`, `30д`, `Создать`.
9. Открыть detail и увидеть `condition_logic = all`.
10. Изменить температуру в HA выше порога и проверить старт записи.

## Принятые Решения

- Автоматически группы не создавать.
- Выбор групп показывать в конце мастера, после сборки правила и до
  подтверждения.
- Группы выбирать как multi-select с галочками; `Далее` доступна даже без
  выбранных групп.
- `crossed_above/crossed_below` скрыть до готовности миграции и matcher.
- Датчики и условия можно выбирать из всех комнат, список разбивать по комнатам.
- В мастере показывать все поддерживаемые типы датчиков, а не только заранее
  известные numeric sensors; невозможные сочетания отсеивать на выборе оператора
  и валидации.
