# Рабочие экраны: адаптер r1

Дата: 6 ноября 2026 года. Ветка `feat/html-interface-migration`.

Реализовано HTML-представление существующих `View`, персональный выбор вида,
приём запросов карточек и передача действий в штатный router. Это код для
основного бота, отдельный от виртуального демо `p1`. Проверка выполняется на
локальных SQLite/HA/Telegram-заглушках. 6 ноября 2026 года, после разрешения
владельца, дополнительно проверены экраны на реальном HA и доставка через
Telegram API. Физические команды и ручная приёмка в нативных клиентах
не входили в эту проверку; результаты и повторный запуск приведены ниже.

## Просмотр и включение

Без HA откройте `ui/widgets/dist/release-preview.html`: реальные HTML/CSS/JS
компонента отображают явно обозначенные примеры данных. Есть темы, размеры,
русский и английский интерфейсы, длинные страницы и ошибки. Сеть не требуется.

Для основного бота с локальным мок-HA предусмотрены поля:

```json
{
  "widget_demo_enabled": false,
  "html_widgets_enabled": true,
  "ha_mock_enabled": true
}
```

Это фрагмент существующего options.json; токен и остальные поля сохраняются.
Локальный `cargo run` теперь запускает основной бот с этими флагами. В Telegram
отправьте `/start`. Источник устройств — сохраняемый в SQLite мок: четыре комнаты,
свет, розетка, климат, датчики с историей и сценарии. Это основной router и
адаптер r1, а не прежнее изолированное демо p1. К `DATABASE_PATH` добавляется
`.mock.sqlite3`; основная БД и реальный HA не используются. Для нового владельца
тестового дома включается HTML, затем выбор сохраняется. На экранах указан
«Тестовый дом». Голосовой HA pipeline и камеры мок не эмулирует.

После восстановления доступа к настоящему дому `ha_mock_enabled: false`
возвращает исходную БД и HA-настройки. Сам мок по умолчанию выключен.

В основном боте по умолчанию используется обычный вид. «Мои настройки → Вид
интерфейса» и `/ui` открывают выбор. `/html` и `/classic` меняют представление
текущего маршрута просмотра. Сохраняется пользовательское предпочтение и
положение в исходном списке; физическая команда из текущего контекста не
воспроизводится. Обновление HTML сохраняет номер внутренней страницы, пока
остаётся тот же маршрут.

Предпочтение находится в `users.interface_mode`; миграция назначает существующим
пользователям `classic`. Удаление пользователя удаляет выбор. Запрос со старым
`admission_generation` не может изменить предпочтение повторно добавленного
пользователя. Новые варианты PersonalPayload добавлены в конец enum, чтобы
не менять кодировки существующих callback-кнопок.

## Покрытие

| Экран | Представление |
|---|---|
| Главная | Все существующие входы и избранное, с пагинацией |
| Комнаты / устройства комнаты | Исходные доступные пользователю строки и действия |
| Карточка устройства без изображения | Состояние и существующие кнопки; те же права и команды |
| Личные настройки, уведомления, избранное | Исходные функции и новый выбор вида |
| Подробности устройства, помощь | Текст и действия с разбиением на части |
| Сценарии и группы | Списки, карточки, исходные команды, результаты и подтверждения |
| Админка, права, настройки устройств, расписания, правила записи | Все текстовые callback-экраны и существующие проверки доступа |
| Камеры и архив | Списки, сведения, фильтры и управление; страницы с изображением остаются обычными |
| Текстовые формы | HTML-инструкция, отмена и действия; ответ сообщением в чат через существующий диалог |
| Графики датчиков | HTML-обзор истории, периоды, сдвиг, свой интервал и исходные действия |
| Остальные изображения и медиа | Обычные сообщения/вложения Telegram с сохранением HTML-предпочтения |

В комнате имя устройства открывает карточку, а отдельная кнопка включает или выключает свет. Такое же действие есть в карточке. При отсутствии права управления либо неизвестном состоянии команда не предлагается. Критичное действие проходит прежнее серверное подтверждение.

Входы в неподдержанные разделы остаются доступными. Если карточка не помещается
в лимиты или Telegram не принял HTML, бот отправляет обычное представление.
Режим в БД не меняется. Следующий поддержанный экран снова использует HTML.

Ограничение по перечню маршрутов снято: общий адаптер переносит любое текстовое
View, чьи кнопки содержат существующие callback Payload. Графики числовых и
бинарных датчиков получили отдельный HTML-компонент. Остальные изображения и
неподдержанные типы кнопок не отбрасываются: весь экран использует обычный вид.
Отдельного HTML-редактора текста и встраивания произвольных изображений пока нет.

## Транспорт и допуск

При `html_widgets_enabled: true` работает один polling-поток через официальный
Telegram beta API: message, callback_query и widget_query. В stable Teloxide
0.17 нет этих HTML-типов; обычные маршруты остаются на его dispatcher. Обновление
пакета не заменяет адаптер: опубликованный latest на дату проверки — 0.17.0,
его документация заявляет Bot API 9.1. Новых зависимостей не добавлено.

Сырой widget_query преобразуется в callback с исходным пользователем, чатом
и ID сообщения. Сохраняются обычные проверки личного чата, допуска и поколения
пользователя. После них адаптер проверяет текущую HTML-сессию, источники данных
View, права, ревизию и серверную таблицу кнопок. Клиент передаёт только ключ;
произвольный Payload из HTML не принимается.

Сессия содержит исходный View, набор разрешённых Payload и случайную ревизию.
Первое действие атомарно помечает ревизию использованной под UI-lock; повтор
не попадает в router. Действие исполняется тем же существующим обработчиком:
с прежними ACL, подтверждениями, журналом и отменой устаревшего результата.
Адаптер сам не вызывает HA-сервисы.

После рестарта таблица HTML-сессий создаётся заново. Запросы старых карточек
не принимаются; `/start` открывает актуальное меню в сохранённом виде. Если
нужно отключить HTML целиком, `html_widgets_enabled: false` сохраняет штатный
Teloxide polling и обычную доставку.

## Контракт и ограничения

Запрос: `r1:<rev>:<key>`, не более 64 байт. `rev` — 32 hex-символа; key разрешён
только в выданном сервером экране. `read` вызывает безопасный `for_refresh()`
текущего маршрута, не прошлую команду. Для открытой формы без незавершённого
действия он возвращает текущую часть с новым `seq`, сохраняя состояние диалога
и ревизию черновика. Фоновые обновления не заменяют открытый HTML-ввод.
`pN` перелистывает сохранённые части после
повторной проверки допуска. Остальные ключи ссылаются на исходные кнопки View.

Модель страницы:

```text
v, rev, seq, s?, lang, title, context, kind, hint?, body, notice, alert,
b[rows of [text,key,kind]], read, back?, graph?, prev, next, page, pages
```

У каждого ряда 1–2 кнопки, всего до 4 рядов; временная навигация графика
допускает 3 кнопки в одном ряду. Поле `b` хранит кнопки кортежами,
сокращая повторяющиеся имена полей; клиент также читает прежние объекты в `rows`.
Обе формы одновременно не допускаются. Размер модели до 1000 байт UTF-8:
`{"page":...}` также укладывается в 1024 байта ответа Telegram. Порядок исходных
кнопок, все предупреждения и текст сохраняются. Неделимые слишком большие
элементы приводят к fallback всего экрана. `seq` упорядочивает ответы и push
внутри процесса; случайный rev не используется для сравнения времени.

`s` обозначает безопасный маршрут текущего экрана. Обновление ревизии и
состояния того же экрана не сбрасывает локальную часть; переход на другой
маршрут или серверную страницу начинает её с первой части. Старые модели
без `s` сохраняют прежнее поведение. В комнате сводка и результат команды
вынесены после кнопок: появление сообщения не меняет разбиение управления.
Если состав кнопок изменился, сервер сохраняет
в поле зрения устройство, из которого пришла команда.

`back` повторяет ключ исходной кнопки «Назад» на каждой серверной странице.
Постоянный контрол сверху возвращает к родительскому экрану; стрелки «Часть»
и «Страница» перелистывают содержимое текущего экрана. Цель возврата берётся
из общего построителя кнопок, поэтому сохраняются комната, страница списка
и контекст мастера. Это обычный callback с прежними проверками допуска.
На корневом экране поле отсутствует; старые модели без `back` поддерживаются.
Повторные кнопки возврата и обновления убраны из содержимого, их действия
доступны через постоянные контролы. Таблица исходных callback остаётся полной.

Карточка занимает доступную ширину пузыря (`width: 0`) при фиксированной
высоте 600 px. Во время запроса подпись обновления меняется без добавления
строки и сдвига кнопок. Нижний отступ учитывает метаданные Telegram через
`env(safe-area-inset-bottom)`. В устройстве и климате сначала показаны краткое подтверждённое
состояние и управление. Полный текст и уведомления сохранены в продолжении.
У рабочего дома подписи под карточкой нет. В режиме mock остаётся только
отметка виртуальных устройств, без подсказок `/ui` и `/classic`.
Сменить вид можно через настройки или прежние команды. Размер целей нажатия
не меньше 44 px; при узкой ширине доступно локальное перелистывание.

### Подтверждение состояния устройства

`html_ui::pending` хранит ожидание по пользователю и устройству отдельно от
ревизии сообщения. Запись создаётся после проверок доступа и подтверждения
критичного действия, перед фактическим вызовом HA. Она связывает исходное
допущение пользователя, идентификатор entity и ожидаемое значение.

Команды `light`/`switch` включения, выключения и переключения ждут `on`/`off`.
Изменение уставки `climate` использует разрешённую очередь команд и ждёт
`attributes.temperature` с точностью 0.001. Произвольные сценарии не получают
фиктивного процента выполнения: у них нет единственного ожидаемого состояния.

В данных кнопок `wait` означает ожидание, `uncertain` — неизвестный исход.
Оба вида блокируют callback; `wait` дополнительно показывает круговой индикатор. Запас
байтов под самый длинный вид резервируется при разбиении страниц, поэтому
смена фазы сама по себе не переносит кнопки. Защита от повторной отправки
проверяется как при обработке ключа виджета, так и перед вызовом HA.

Наблюдатель только читает HA, не чаще раза в секунду, не более 30 секунд после
ответа на отправку. Подтверждённое значение запрашивает обновление через общую
очередь текущего экрана; пропуск обновления из-за занятого UI повторяется.
Блокировку снимает свежий снимок комнаты или устройства с нужным значением.
Снимок, начатый до команды, или чтение во время отправки её не снимает.
Окончание ожидания не возвращает пользователя на старый экран.

После тайм-аута или ошибки только явное обновление с известным значением либо
позднее наблюдение ожидаемого состояния возвращает управление. Проверка всех
неподтверждённых устройств выполняется одним чтением с ограничением 3 секунды.
Удаление HTML-сессии отменяет наблюдателей; смена допуска, цели или архивация
устройства прекращает старое ожидание. Задачи входят в существующий механизм
завершения фоновых задач. Реальные команды при автоматических проверках не
отправляются: задержки и отказы моделирует тестовый HA.

### Графики датчиков

Первая страница содержит график, текущее значение и выбор периода: 12/24 часа, 3/7 суток.
Сдвиг окна на сутки, текущее окно, собственный интервал, сведения, избранное
и уведомления используют прежние маршруты. Подробности и второстепенные кнопки
доступны в продолжении. Собственный интервал вводится сообщением в чат;
после завершения формы бот возвращает график с сохранённым смещением окна.

`graph` находится только на первой странице и содержит `plot`, `top`, `bottom`,
`start`, `end`. История разделена на 32 равных интервала. В каждом сохраняются
минимум, максимум и последнее значение с квантованием в 64 уровня. Это обзор,
а не полный ряд исходных измерений: короткие пики видны как диапазон.
Интервал, хотя бы частично перекрывающий отсутствие данных, остаётся разрывом.
Начальное значение берётся только из фактической истории; отсутствие данных
не заменяется нулём. Бинарные состояния учитывают инверсию и пользовательские
подписи так же, как обычный график. Текущий показатель передаётся без квантования;
полный текст сохранён в продолжении. Классический вид использует исходный PNG.

`plot` — 96 ASCII-символов: тройки min/max/last из алфавита
`ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-_`; `...` означает
разрыв. Поля осей и времени — текст, без HTML и внешних URL. Размер всей страницы,
включая график и управление, остаётся не более 1000 байт.

`graph.html` и `release.html` используют общий обработчик r1. Код отправленного
виджета неизменяем, поэтому переход между графиком и обычной карточкой создаёт
новое сообщение через существующий механизм смены представления. Смена периода
и обновление изменяют данные текущего графика. Старые карточки не принимают
действия после смены текущего сообщения.

`kind`: menu, device, climate, confirmation, form или list. Поле влияет только
на оформление; `hint` содержит текст подсказки формы на первой серверной
странице. Старые модели без этих полей поддерживаются. Для длинного нового
HTML-экрана используется одна серверная пагинация; переход с обычной текстовой
страницы сохраняет её исходное положение и кнопки перехода.

Ответ `{"accepted":true}` подтверждает только приём запроса. Состояние приходит
отдельно через `editMessageWidgetData`; клиент ждёт более новый seq. ACK отправляется
один раз после проверки допуска, до передачи запроса обработчику и ожидания HA. После
таймаута действия блокируются до успешного read с новым состоянием. Поздний
старый ответ и поздний push команды после ошибки сами не снимают блокировку.
Отказ `{"denied":true}` скрывает данные; пересланная карточка их не отображает.

HTML-артефакт ограничен 32768 байтами исходника и 4096 байтами zlib level 9.
Сборка использует существующий набор токенов. `npm run build` обновляет
`dist/release.html`, manifest и автономный preview; Node.js не нужен при
обычном запуске Rust со встроенным `include_str!`.

## Проверки

Rust проверяет реальные маршруты на сохранение всех кнопок и текстов, размеры
каждого пакета, личный чат, подмену ресурса, отзыв/повторный допуск, одноразовый
claim, пагинацию, fallback и безопасную смену вида при action-контексте.
Интеграционные проверки проходят через основные обработчики на мок-HA:
22 маршрута управления, подтверждение с повторным нажатием, ввод температуры
с ошибкой и успешным ответом, сохранение черновика расписания и длинные формы.
Браузер проверяет все части 39 примеров обычных экранов и 16 примеров графиков
в двух темах и четырёх ширинах — 440 сочетаний, точное сохранение
текста/кнопок/подсказок, recovery, оба порядка ACK/push, старые ответы
и совместимость прежних моделей.

Для приёмки применяется копия исходной SQLite-базы, созданная через соединение
только для чтения. Рабочие настройки, права, сессии и флаг `ha_mock_enabled`
не меняются. Тестовый HA-клиент запрещает оба метода вызова сервисов;
фоновые задачи, запись камер и голосовой pipeline не запускаются. Запросы
кнопок проверяются на локальной заглушке Telegram; отдельная проверка реального
API не вызывает `getUpdates` и не конкурирует с работающим ботом.

Повторный запуск из корня репозитория после предоставления доступа к HA:

```sh
cargo test live_readonly_html_screens -- --ignored --nocapture
```

Для дополнительной отправки, изменения и удаления тестовых сообщений владельцу
настроенного бота добавьте `HA_UI_TELEGRAM_SMOKE=1` перед командой. Токен берётся
из настроек и не выводится. Команда печатает путь `target/live-ui-...`, содержащий
копию БД, `report.json` и `fixtures.json`. Это реальные данные дома; каталог
`target` исключён из Git. Подставьте абсолютный путь к полученному файлу:

```sh
HA_WIDGET_LIVE_FIXTURES=/absolute/path/target/live-ui-.../fixtures.json npm --prefix ui/widgets run check:browser
```

Браузер работает без сети и сохраняет рядом `browser-report.json` и снимки
в `screenshots/`. По умолчанию live-тест пропускается. Обычный `cargo test`
не обращается к домашнему HA. Результаты не подтверждают выполнение физических
команд, съёмку камер, события WebSocket или отображение в Telegram iOS/Android;
эти сценарии остаются отдельной приёмкой. Дополнительная схема для запуска
проверок не требуется: последовательность отражена в командах выше.
