# Рабочие экраны: адаптер r1

Дата: 6 ноября 2026 года. Ветка `feat/html-interface-migration`.

Реализовано HTML-представление существующих `View`, персональный выбор вида,
приём запросов карточек и передача действий в штатный router. Это код для
основного бота, отдельный от виртуального демо `p1`. Проверка выполняется на
локальных SQLite/HA/Telegram-заглушках. Соединений с реальным HA не выполнялось.
Проверка на настоящем доме и нативных клиентах остаётся этапом приёмки после
разрешения владельца, а не подтверждённым результатом этого изменения.

## Просмотр и включение

Без HA откройте `ui/widgets/dist/release-preview.html`: реальные HTML/CSS/JS
компонента отображают явно обозначенные примеры данных. Есть темы, размеры,
русский и английский интерфейсы, длинные страницы и ошибки. Сеть не требуется.

Для основного бота с локальным мок-HA предусмотрены поля:

```json
{
  "widget_demo_enabled": false,
  "html_widgets_enabled": true,
  "ha_mock_enabled": true
}
```

Это фрагмент существующего options.json; токен и остальные поля сохраняются.
Локальный `cargo run` теперь запускает основной бот с этими флагами. В Telegram
отправьте `/start`. Источник устройств — сохраняемый в SQLite мок: четыре комнаты,
свет, розетка, климат, датчики с историей и сценарии. Это основной router и
адаптер r1, а не прежнее изолированное демо p1. К `DATABASE_PATH` добавляется
`.mock.sqlite3`; основная БД и реальный HA не используются. Для нового владельца
тестового дома включается HTML, затем выбор сохраняется. На экранах указан
«Тестовый дом». Голосовой HA pipeline и камеры мок не эмулирует.

После восстановления доступа к настоящему дому `ha_mock_enabled: false`
возвращает исходную БД и HA-настройки. Сам мок по умолчанию выключен.

В основном боте по умолчанию используется обычный вид. «Мои настройки → Вид
интерфейса» и `/ui` открывают выбор. `/html` и `/classic` меняют представление
текущего маршрута просмотра. Сохраняется пользовательское предпочтение и
положение в исходном списке; физическая команда из текущего контекста не
воспроизводится. Обновление HTML сохраняет номер внутренней страницы, пока
остаётся тот же маршрут.

Предпочтение находится в `users.interface_mode`; миграция назначает существующим
пользователям `classic`. Удаление пользователя удаляет выбор. Запрос со старым
`admission_generation` не может изменить предпочтение повторно добавленного
пользователя. Новые варианты PersonalPayload добавлены в конец enum, чтобы
не менять кодировки существующих callback-кнопок.

## Покрытие

| Экран | Представление |
|---|---|
| Главная | Все существующие входы и избранное, с пагинацией |
| Комнаты / устройства комнаты | Исходные доступные пользователю строки и действия |
| Карточка устройства без изображения | Состояние и существующие кнопки; те же права и команды |
| Личные настройки, уведомления, избранное | Исходные функции и новый выбор вида |
| Подробности устройства, помощь | Текст и действия с разбиением на части |
| Сценарии и группы | Списки, карточки, исходные команды, результаты и подтверждения |
| Админка, права, настройки устройств, расписания, правила записи | Все текстовые callback-экраны и существующие проверки доступа |
| Камеры и архив | Списки, сведения, фильтры и управление; страницы с изображением остаются обычными |
| Текстовые формы | HTML-инструкция, отмена и действия; ответ сообщением в чат через существующий диалог |
| Графики, изображения, медиа | Обычные сообщения/вложения Telegram с сохранением HTML-предпочтения |

В комнате имя устройства открывает карточку, а отдельная кнопка включает или выключает свет. Такое же действие есть в карточке. При отсутствии права управления либо неизвестном состоянии команда не предлагается. Критичное действие проходит прежнее серверное подтверждение.

Входы в неподдержанные разделы остаются доступными. Если карточка не помещается
в лимиты или Telegram не принял HTML, бот отправляет обычное представление.
Режим в БД не меняется. Следующий поддержанный экран снова использует HTML.

Ограничение по перечню маршрутов снято: общий адаптер переносит любое текстовое
View, чьи кнопки содержат существующие callback Payload. Это сохраняет состав
действий новых и старых разделов. Изображения и неподдержанные типы кнопок не
отбрасываются: весь экран использует обычный вид. Отдельного HTML-редактора
текста и встраивания изображений в HTML пока нет.

## Транспорт и допуск

При `html_widgets_enabled: true` работает один polling-поток через официальный
Telegram beta API: message, callback_query и widget_query. В stable Teloxide
0.17 нет этих HTML-типов; обычные маршруты остаются на его dispatcher. Обновление
пакета не заменяет адаптер: опубликованный latest на дату проверки — 0.17.0,
его документация заявляет Bot API 9.1. Новых зависимостей не добавлено.

Сырой widget_query преобразуется в callback с исходным пользователем, чатом
и ID сообщения. Сохраняются обычные проверки личного чата, допуска и поколения
пользователя. После них адаптер проверяет текущую HTML-сессию, источники данных
View, права, ревизию и серверную таблицу кнопок. Клиент передаёт только ключ;
произвольный Payload из HTML не принимается.

Сессия содержит исходный View, набор разрешённых Payload и случайную ревизию.
Первое действие атомарно помечает ревизию использованной под UI-lock; повтор
не попадает в router. Действие исполняется тем же существующим обработчиком:
с прежними ACL, подтверждениями, журналом и отменой устаревшего результата.
Адаптер сам не вызывает HA-сервисы.

После рестарта таблица HTML-сессий создаётся заново. Запросы старых карточек
не принимаются; `/start` открывает актуальное меню в сохранённом виде. Если
нужно отключить HTML целиком, `html_widgets_enabled: false` сохраняет штатный
Teloxide polling и обычную доставку.

## Контракт и ограничения

Запрос: `r1:<rev>:<key>`, не более 64 байт. `rev` — 32 hex-символа; key разрешён
только в выданном сервером экране. `read` вызывает безопасный `for_refresh()`
текущего маршрута, не прошлую команду. Для открытой формы без незавершённого
действия он возвращает текущую часть с новым `seq`, сохраняя состояние диалога
и ревизию черновика. Фоновые обновления не заменяют открытый HTML-ввод.
`pN` перелистывает сохранённые части после
повторной проверки допуска. Остальные ключи ссылаются на исходные кнопки View.

Модель страницы:

```text
v, rev, seq, lang, title, context, kind, hint?, body, notice, alert,
rows[{text,key,kind}], read, prev, next, page, pages
```

У каждого ряда 1–2 кнопки, всего до 4 рядов. Размер модели до 1000 байт UTF-8:
`{"page":...}` также укладывается в 1024 байта ответа Telegram. Порядок исходных
кнопок, все предупреждения и текст сохраняются. Неделимые слишком большие
элементы приводят к fallback всего экрана. `seq` упорядочивает ответы и push
внутри процесса; случайный rev не используется для сравнения времени.

`kind`: menu, device, climate, confirmation, form или list. Поле влияет только
на оформление; `hint` содержит текст подсказки формы на первой серверной
странице. Старые модели без этих полей поддерживаются. Для длинного нового
HTML-экрана используется одна серверная пагинация; переход с обычной текстовой
страницы сохраняет её исходное положение и кнопки перехода.

Ответ `{"accepted":true}` подтверждает только приём запроса. Состояние приходит
отдельно через `editMessageWidgetData`; клиент ждёт более новый seq. ACK отправляется
один раз после проверки допуска, до передачи запроса обработчику и ожидания HA. После
таймаута действия блокируются до успешного read с новым состоянием. Поздний
старый ответ и поздний push команды после ошибки сами не снимают блокировку.
Отказ `{"denied":true}` скрывает данные; пересланная карточка их не отображает.

HTML-артефакт ограничен 32768 байтами исходника и 4096 байтами zlib level 9.
Сборка использует существующий набор токенов. `npm run build` обновляет
`dist/release.html`, manifest и автономный preview; Node.js не нужен при
обычном запуске Rust со встроенным `include_str!`.

## Проверки

Rust проверяет реальные маршруты на сохранение всех кнопок и текстов, размеры
каждого пакета, личный чат, подмену ресурса, отзыв/повторный допуск, одноразовый
claim, пагинацию, fallback и безопасную смену вида при action-контексте.
Интеграционные проверки проходят через основные обработчики на мок-HA:
22 маршрута управления, подтверждение с повторным нажатием, ввод температуры
с ошибкой и успешным ответом, сохранение черновика расписания и длинные формы.
Браузер проверяет все части 23 примеров в двух темах и четырёх ширинах — 184
сочетания, точное сохранение текста/кнопок/подсказок, recovery, оба порядка
ACK/push, старые ответы и совместимость прежних моделей.
